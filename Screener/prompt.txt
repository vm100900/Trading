

Act as an expert quantitative developer and algorithmic trading systems architect specializing in **Rust**, financial-data systems, Interactive Brokers TWS/API, asynchronous programming, and high-performance market-data processing.

Build a **production-quality, highly efficient multi-stage stock and ETF screener in Rust** that implements a strict sequential multi-timeframe technical filter.

The primary architectural objective is to **minimize Interactive Brokers historical-data API requests** by eliminating as many symbols as possible during the inexpensive daily screening stage.

The screening pipeline must be strictly sequential:

```text
Full Universe
    ↓
Phase 1 — Daily Macro Filter via Yahoo Finance
    ↓
Phase 2 — 30-Minute Micro-Trend Filter via IBKR
    ↓
Phase 3 — 2-Minute Intraday + VWAP Filter via IBKR
    ↓
Final Watchlist
```

A symbol that fails a phase must **never** proceed to the next phase.

---

# 1. Technology Requirements

Implement the application entirely in **Rust**.

Prefer stable Rust and idiomatic asynchronous Rust.

Use appropriate Rust crates for:

* HTTP/API communication
* Yahoo Finance data retrieval
* Interactive Brokers API communication
* asynchronous execution
* JSON/configuration
* CSV parsing if needed
* date/time and timezone handling
* structured logging
* error handling

If a mature direct Rust client for a required API is unavailable, implement the required protocol/API interaction cleanly rather than switching the project to Python.

Do not use Python, `yfinance`, or `ib_insync` in the implementation. Their functionality should be reproduced using appropriate Rust libraries/APIs.

Use an architecture based on:

* `tokio`
* async/await
* strongly typed structs/enums
* `Result`-based error handling
* centralized configuration
* structured logging

Avoid unnecessary dependencies.

Do not interpret "260 days" as 260 calendar days.

The implementation must guarantee at least:

```text

```

# 7. Phase 1 SMA200 Slope

The SMA200 slope period is **exactly 5 trading sessions**.

Do not use 7 sessions.

Define the positive slope condition as:

```text
SMA200[current]
>
SMA200[5 completed trading sessions ago]
```

Formally:

```rust
sma200_current > sma200_5_bars_ago
```

The comparison must be based on trading bars, not calendar days.

---

# 8. Phase 1 Filter

A symbol survives Phase 1 ONLY if all conditions are true:

```text
Latest completed daily close
    >
SMA10
    >
SMA20
    >
SMA50
    >
SMA200
```

AND:

```text
SMA200[current]
    >
SMA200[5 trading bars ago]
```

Equivalent logic:

```text
close > sma10
&& sma10 > sma20
&& sma20 > sma50
&& sma50 > sma200
&& sma200_current > sma200_5_bars_ago
```

Any missing indicator, insufficient data, invalid value, or malformed dataset causes the symbol to fail Phase 1.

The latest daily price must mean:

```text
latest completed daily close
```

Do not use a live/intraday price for Phase 1.

# 14. Phase 2 SMA65 Slope

Require:


```rust

```

Do not use the currently forming 30-minute bar.

# 19. Phase 3 Daily VWAP

Calculate **current-session RTH VWAP only**.

VWAP must reset at:

```text
09:30 America/New_York
```

Previous trading sessions must not contribute to the current day's VWAP.

For each current-session 2-minute bar:

```text
Typical Price = (High + Low + Close) / 3
```

Then:

```text
VWAP =
Σ(Typical Price × Volume)
/
Σ(Volume)
```

Only current-session RTH bars may be included.

The VWAP used for the signal must correspond to the latest completed 2-minute bar.

If cumulative session volume is zero or invalid, do not generate a signal.


# 21. No Look-Ahead Bias

This is a hard requirement.

Never evaluate any signal using an incomplete bar.

Use:

```text
Phase 1 → latest completed daily bar
Phase 2 → latest completed 30-minute bar
Phase 3 → latest completed 2-minute bar
```

The screener must be reproducible using historical data available at the signal timestamp.

---

# 22. IBKR Rate Limiting

Implement a **centralized asynchronous historical-data rate limiter**.

Do not rely merely on:

```text
sleep(1 second)
```

between individual requests.

The limiter must coordinate all IBKR historical-data requests across Phase 2 and Phase 3.

Use Tokio-compatible asynchronous delays rather than blocking the runtime.

The architecture should support:

* configurable request intervals
* controlled concurrency
* retry handling
* exponential backoff
* randomized jitter
* pacing-error detection
* connection-error recovery where appropriate

Do not retry indefinitely.

The system must prioritize IBKR pacing compliance over maximum request concurrency.

---

# 23. Controlled Concurrency

Do not issue unrestricted batches of historical requests.

Avoid launching hundreds of simultaneous requests.

Use a controlled asynchronous worker/request-queue architecture.

The desired behavior is:

```text
Phase 1 survivors
       ↓
Rate-limited request queue
       ↓
IBKR
       ↓
Results
```

The same centralized pacing mechanism must protect both Phase 2 and Phase 3.

# 30. Efficiency Requirements

The implementation must optimize for API efficiency.

For example, if:

```text
1,000 symbols
```

enter Phase 1 and only:

```text
150 symbols
```

survive, Phase 2 must process only those 150.

If only:

```text
30 symbols
```

survive Phase 2, Phase 3 must process only those 30.

Never re-expand the universe between phases.

The number of IBKR requests should therefore be approximately proportional to the number of symbols surviving the previous phase.

# 33. Exact Mathematical Specification

Do not modify these rules.

### Phase 1

```text
Close > SMA10 > SMA20 > SMA50 > SMA200
```

AND:

```text
SMA200[t] > SMA200[t-5]
```

where `t-5` means five completed trading sessions before the current completed daily bar.

### Phase 2

```text
Close_30m > SMA7 > SMA17 > SMA33 > SMA65
```

AND:

```text
SMA65[t] > SMA65[t-1]
```

where both bars are completed 30-minute bars.

### Phase 3

```text
Close_2m > SMA20 > SMA50 > SMA100
```

AND:

```text
Close_2m > CurrentSessionVWAP
```

All comparisons must be strict `>` comparisons.

Do not substitute `>=`.
